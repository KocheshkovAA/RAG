# Prompt regression: стабильность, интерпретируемость, воспроизводимость

Каждый промпт в проекте — это неявный контракт с моделью, который может незаметно сломаться при
любой правке (своей или в ответ на смену провайдера/модели). Этот документ — не абстрактная
методология, а инвентарь: какой промпт за что отвечает, что реально проверяет его на регресс
сегодня, и где проверки честно нет. Плюс один живой, только что пойманный кейс — конкретная
демонстрация, зачем это нужно, а не гипотетическая.

## Живой кейс: как регресс-смоук поймал реальную нестабильность

При работе над п.8 плана в `data/eval/smoke_cases.json` добавлены два кейса
(`faithfulness_strictness_necrons`, `faithfulness_strictness_viliar_ifiss`) — конкретные вопросы
из живой отладки faithfulness-порога (`a928312`), которые раньше ложно отказывались при
zero-tolerance политике. Два подряд прогона `make smoke` (без единой правки кода между ними) дали:

- Прогон 1: `faithfulness_strictness_necrons` — FAIL (refused=true), `faithfulness_strictness_viliar_ifiss` — FAIL.
- Прогон 2 (через пару минут): `faithfulness_strictness_necrons` — PASS, `faithfulness_strictness_viliar_ifiss` — FAIL.

Прямая проверка одного и того же вопроса ("Кто такие некроны?") между прогонами показала разные
`faithfulness_score` (0.6-0.75 в разных вызовах) при одинаковом `min_score=0.7` — то есть система
балансирует ровно на границе порога, и один и тот же вопрос может пройти или не пройти в
зависимости от конкретной генерации (модель не даёт identical claims/quotes от вызова к вызову
даже при `temperature=0` для faithfulness-роли — сама генерация ответа идёт с `temperature=0.15`,
так что заново генерируемые claims тоже варьируются).

**Честный вывод**: порогово-based фикс (`a928312`) снизил refusal_rate (60% → 30% на 10-вопросном
прогоне), но не устранил нестабильность полностью — она теперь встречается реже, но всё ещё
воспроизводима. Это не баг конкретной правки, а следствие того, что faithfulness-порог 0.7
находится близко к типичному диапазону доли подтверждённых claims для этой модели/промпта. Открытый
вопрос для следующей итерации: либо снизить `min_score`, либо дальше ужесточать промпт извлечения
цитат, либо оба — не решено здесь единолично, см. `docs/rnd-decision-log.md`.

## Отдельная, не связанная находка

`simple_fact_abaddon` (уже существовавший смоук-кейс, не добавлен сегодня) стабильно проваливается
по другой причине: роутер стабильно (3/3 повторных вызовов `classify_route`) отправляет вопрос
"Как Чернокаменные крепости связаны с Абаддоном?" на `graph`-маршрут, а LightRAG (индексирована
только статья «Ересь Хоруса» — сознательное ограничение scope, см. `docs/agent-architecture.md`)
не находит по нему данных → `graph-empty` → отказ. Это не регрессия от сегодняшних правок — кейс,
похоже, был написан в расчёте на `vector`-маршрут, а роутер закономерно относит вопрос про Абаддона
к Ереси Хоруса. Не чинил в рамках этой сессии — либо переписать сам кейс под другой вопрос, либо
расширить LightRAG-корпус (последнее уже сознательно отклонено как решение, см. project-заметки).

## Практика: когда FAIL — это регрессия, а не шум

Учитывая продемонстрированную выше стохастичность, `make smoke`/`compare_router.py` нельзя
трактовать как "один FAIL = откат правки". Практическое правило:

1. Один FAIL на faithfulness-связанном кейсе → перезапустить `make smoke` 1-2 раза перед выводами.
2. FAIL, стабильно воспроизводимый 3/3 → реальная регрессия, разбирать.
3. Router-кейсы (`compare_router.py`) — доверять accuracy на 27 примерах больше, чем единичному
   вопросу, по той же причине (единичный вызов LLM не идеально детерминирован даже на temperature=0,
   см. `planning/progress_log.md` — то же наблюдение уже фиксировалось при сравнении LoRA/промпт-
   классификатора).

## Ещё один живой кейс: непойманная нестабильность под нагрузкой

При перепрогоне полного 60-вопросного eval для обновления цифр в README (`d9fc3f5`, тот же день)
3 из 60 vector-вопросов упали с `'NoneType' object is not iterable` — несмотря на уже добавленный
retry на произвольные исключения (не только rate-limit), т.е. упали 4 раза подряд каждый, не один
раз. При этом ни один из трёх вопросов не воспроизвёлся при изолированном повторном вызове сразу
после прогона — значит, сбой специфичен для состояния под устойчивой последовательной нагрузкой
(60 вопросов подряд), а не для конкретного вопроса или промпта. Точный источник не найден (не
хватило времени копать глубже в рамках этой сессии) — вероятный кандидат: `asyncio.gather()` в
`vectorrag.py` иногда получает `None` вместо списка документов от одной из parallel-ветвей retrieval
под нагрузкой, но это не подтверждено трассировкой. Зафиксировано как открытый пробел, а не тихо
сглажено — при подсчёте метрик в README эти строки помечены явно, а не просто исключены из
знаменателя без объяснения.

## Честный пробел, не закрытый

Нет инфраструктуры replay/mock-LLM тестирования, которая давала бы ПОЛНОСТЬЮ детерминированный
регресс-прогон (записанные реальные ответы модели, воспроизводимые без сети) — все текущие проверки
либо используют фейковый LLM (быстро, детерминированно, но проверяет только логику вокруг промпта,
не сам промпт), либо бьют по живому API (проверяет промпт, но с шумом от недетерминизма модели).
Закрытие этого пробела — отдельная, более крупная задача (снапшот-тестирование LLM-ответов),
сознательно не взятая в этой сессии.
