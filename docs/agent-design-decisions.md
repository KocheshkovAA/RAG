# Decision framework: deterministic code / tool / agent / sub-agent

Прямое требование из разбора вакансии Финама: не просто "мы используем агентов", а показать
осознанность выбора — когда достаточно детерминированного кода, когда нужен просто tool,
когда реально нужен agent с автономным решением, когда — отдельный sub-agent, и когда агента
использовать не стоит вообще. Ниже — не абстрактная теория, а разбор пяти категорий на
**реальных компонентах этого проекта**, плюс один маленький worked example (`CriticSubAgent`),
показывающий границу между guard и sub-agent на практике.

## Критерий по каждой категории

| Категория | Когда это правильный выбор | Пример из проекта |
|---|---|---|
| **Deterministic-код** | Решение полностью описывается фиксированным правилом — не требует суждения о неопределённости, результат предсказуем по входу | `RetrievalGate.filter_docs()` (порог по score), `slowapi` rate-limit, Redis-кэш по ключу вопроса, `insufficient_response()` (фиксированный текст отказа) |
| **Tool** | Нужен доступ к внешней системе (retrieval/API/БД) с узким, заранее известным action space — сам вызов не требует суждения, решение "вызывать ли и с чем" принимает что-то снаружи | `search_knowledge_base` (`SearchKnowledgeBase` в `agentic_rag.py`) — один параметр, один эффект (hybrid search), никакой логики внутри самого тула |
| **Agent** | Есть реальная неопределённость: нужно выбрать стратегию, решить продолжать/остановиться, интерпретировать промежуточный результат и адаптировать следующий шаг | `AgenticRAG` — ReAct-цикл: сколько раз и с какими запросами искать, решается по факту того, что уже нашли, не по фиксированному правилу |
| **Sub-agent** | Отдельная специализация или параллельная ветка суждения с собственным state/prompt/eval, не сводимая к узкому guard'у (шире объём оценки, многовариантный, не бинарный, исход) | `CriticSubAgent` (`examples/critic_subagent.py`) — спайк, не подключён к проду, см. ниже |
| **Не агент вообще** | Простая CRUD-интеграция, дешёвый детерминированный пайплайн, слишком высокий риск action misuse, строгий SLA/latency cap | `GET /v1/ready` (health-check), `graph`-маршрут после роутинга (один детерминированный вызов `LightRAGClient.query()`, не цикл) |

## Разбор по категориям

### Deterministic-код

Правило проще и надёжнее LLM-суждения там, где вход→выход однозначны:

- `RetrievalGate` — сравнение score с порогом, никакой неопределённости в решении.
- `slowapi` rate-limit, Redis-кэш ответов (`app/core/cache.py`) — классические инженерные
  механизмы, не решения агента.
- Safety-net в `classify_route()`: `if route == AGENTIC and not settings.AGENTIC_ROUTE_ENABLED:
  return VECTOR` — LLM-классификатор технически МОЖЕТ выбрать `agentic`, даже если фича
  выключена (enum не запрещает), поэтому финальное решение "разрешено ли это в принципе"
  оставлено детерминированному коду, а не доверию к тому, что промпт "правильно попросит".
- `refuse_response()`/`insufficient_response()` — фиксированный текст, не генерируется заново
  каждый раз, чтобы отказ не выдавал сигналов, полезных для probing (см.
  `docs/agent-threat-model.md`).

### Tool

`search_knowledge_base` — единственный инструмент в проде (см. `docs/agent-architecture.md`,
раздел Tools). Узкий специально: один параметр (`query: str`), один эффект (read-only hybrid
search), никакого суждения внутри самого тула — вся логика "когда и с чем вызывать" живёт
СНАРУЖИ, в агенте. MCP-инструменты (`ask_warhammer_lore` и др.) — тот же принцип на уровень
выше: тонкие прокси к API, ноль логики внутри.

Пограничный случай: `QueryOptimizer` (`app/core/query_processor.py`) вызывает LLM для
декомпозиции вопроса на под-запросы — это НЕ agent (нет цикла, нет решения "продолжать ли"),
но и не совсем "инструмент" в смысле внешнего действия. Ближе всего к детерминированному коду
с одним LLM-вызовом внутри — вызывается один раз, безусловно, результат не пересматривается.

### Agent

`AgenticRAG` — единственный настоящий agent в проекте: неопределённость реальна (сколько
раз искать и с какими запросами заранее не известно, зависит от того, что вернул retriever),
решение принимается заново на каждом раунде по факту наблюдения (`docs/agent-architecture.md`,
ReAct). Router (`classify_route()`) — **не** agent, несмотря на LLM-вызов: это одноразовая
классификация без цикла, без итеративного пересмотра решения по наблюдениям — по объёму
суждения он ближе к "LLM в детерминированном pipeline", чем к agent. Стоит явно проговаривать
эту границу на интервью: не каждый LLM-вызов — это агентность.

### Sub-agent

Практический минимум по плану — не строить полноценную multi-agent платформу, а показать ОДИН
маленький пример и явно провести границу guard vs sub-agent. Границу: `AnswerFaithfulnessGuard`
делает LLM-вызовы (два, после сегодняшнего изменения — извлечение claims + entailment-проверка),
но остаётся guard'ом, а не sub-agent'ом:

- Объём суждения узкий и фиксированный: заземлён ли конкретный claim дословно в контексте.
- Исход по сути бинарный (score-порог, `passed`/не `passed`), не более широкое качественное
  суждение.
- Встроен в критический путь КАЖДОГО запроса как обязательная точка — не отдельная,
  вызываемая по необходимости роль.

`CriticSubAgent` (`examples/critic_subagent.py`) — worked example для сравнения:

- Объём суждения шире: полнота ответа на составной вопрос, ясность формулировок, не выдаёт
  ли черновик общее знание о вселенной за специфичный факт (не дублирует буквальную
  заземлённость — это по-прежнему работа guard'а).
- Исход трёхвариантный (`approve`/`revise`/`refuse`) + текстовый `feedback`, предназначенный
  управлять СЛЕДУЮЩИМ шагом (переписать/отказать/принять) — не терминальное условие само по
  себе, а вход для потенциального следующего раунда генерации.
- Не встроен в основной пайплайн — задокументированный, автономно тестируемый спайк
  (`tests/test_critic_subagent.py`, фейковый LLM, без сети).

Честно: многошаговый цикл "draft → critic → revise → critic" здесь не реализован — это
отдельная, более крупная задача (subsumes часть ToT/Reflection-loop дизайна из
`docs/agent-architecture.md`), которую спайк сознательно не берёт на себя. Реализовать его
целиком означало бы обещанное в плане "не превращать проект в multi-agent платформу"
нарушить.

### Когда агента не использовать вообще

- `GET /v1/ready` — детерминированный health-check зависимостей (`app/core/health.py`),
  нет никакого суждения, есть implicit SLA (должен отвечать быстро и предсказуемо) —
  агентность здесь была бы чистым усложнением без выгоды.
- `graph`-маршрут после того, как роутер уже решил — один вызов `LightRAGClient.query()`,
  не цикл: агентность (если бы понадобилась) была бы оправдана ВНУТРИ LightRAG, а не на
  уровне оркестратора, который здесь просто делает один детерминированный HTTP-вызов.
- Ingestion (`scripts/ingest.py`) — batch ETL по расписанию/вручную, никакой неопределённости
  в том, что делать с новыми документами (embed → upsert) — агентность добавила бы риск
  action misuse (см. `docs/agent-threat-model.md`, п. Tool misuse) без выигрыша.
- Общий критерий, не только из этого проекта: если задачу можно правильно решить одним
  детерминированным правилом или одним неитеративным вызовом — использование agent-цикла
  это не "более продвинутое" решение, а немотивированный latency/cost/risk overhead.
